# 05 — Аудит эксплуатации и рантайма codex-lb

- Дата: 2026-10-28. Коммит: `0b674e97` (= тег `go-v1.0.10`). Toolchain: go1.26.6 linux/amd64.
- Зона: `cmd/codex-lb/**`, фоновые сервисы `internal/application` (usage/catalog/automations/warmups/runtime_updates), `internal/adapters/{releases,updatefiles,updatecontrol,webui}`, `deploy/`, `Dockerfile`, `Makefile`, `README.md`, `bin/`, `dist/`, `.local/`.
- Метод: чтение кода и контракта (`openspec/specs/go-runtime`, `runtime-updates`, `graceful-shutdown`, `proxy-runtime-observability`), сборка бинарей в `.local/audit/scratch-ops/`, запуск только на loopback внутри `unshare -rn` (сетевой namespace без внешней сети: проверено `curl api.github.com` → `Could not resolve host`), временные `--data-dir`. Реального трафика к провайдерам, GitHub и VPS не было. systemd-юниты не устанавливались (только `systemd-analyze security --offline`).
- Скрипты замеров: `.local/audit/scratch-ops/{measure,startloop,drain,sigkill,downgrade,errs,probe,reqlog,idle}.sh`, вариант юнита `.local/audit/scratch-ops/codex-lb.hardened.service`.
- Пометка «гипотеза» означает, что вывод следует из кода, но не воспроизведён замером.

## Резюме

1. **Рантайм лёгкий и быстрый.** Старт до `/health/ready` занимает 12–24 мс на тёплой ФС (83–97 мс при первом создании БД), в managed-режиме (launcher + worker) 122–177 мс. В простое: RSS worker около 18 МиБ, launcher около 12 МиБ, CPU 0 тиков за 30 с. SIGTERM в простое завершает процесс за 9–19 мс с кодом 0. Узких мест по скорости старта и обновления нет.
2. **Главная проблема — наблюдаемость.** Во всём рантайме 8 вызовов логгера. В слое `internal/application` логгера нет совсем. Ошибки фоновых опросов отбрасываются через `_ =`, перехваченные паники глотаются без стека. Метрик и pprof нет: `/metrics` и `/debug/pprof/` отвечают `200 text/html`, то есть отдают оболочку SPA. Замер показал, что четыре запроса, отклонённые с `503 no_available_accounts`, не оставили следа ни в логе, ни в БД. Оператор узнаёт о деградации только от клиентов.
3. **Ошибки старта маскируются.** Неверная переменная окружения даёт сообщение «cannot open or migrate Go database; foreign/legacy databases…», а занятый порт — «cannot bind HTTP listen address», без адреса и причины.
4. **Самообновление сложное и устроено с ловушками.** Это ~2550 строк продового кода и ~2540 строк тестов, модель из двух процессов, исполнение бинарей из записываемого data-dir. Ручной даунгрейд заменой `/usr/local/bin/codex-lb` молча игнорируется (замер). Обновление со сменой схемы БД невозможно. Переключение требует, чтобы активной работы не было совсем.
5. **Резервное копирование не организовано.** Есть только один снимок перед обновлением, он лежит в том же data-dir и делается только в managed-режиме. Регулярного или онлайн-бэкапа нет, runbook восстановления нет.
6. **CI нет, релизы собираются вручную** в `dist/` и `.local/release-*`. Чистый checkout не собирается: `pattern all:dist: no matching files found`. При этом сам Go-бинарь воспроизводим бит-в-бит (v1.0.10 amd64, проверено).
7. **systemd-юнит почти без hardening**: `systemd-analyze security` даёт 8.3 EXPOSED. Нет `MemoryMax` и `StartLimit*`. Предложенный вариант оценивается в 1.2 OK, но его нужно проверить на staging.
8. **Много мусора.** 333 МБ в `dist/`, 24 МБ в `bin/`, 487 МБ в `.local/`. Отслеживаются lock-файл агента, устаревшие ссылки в `AGENTS.md`/`.gitattributes` и 188 неархивированных OpenSpec-изменений. Большая часть `openspec/specs` описывает legacy-Python/Helm.

P0 не найдено. Отказы, которые случаются прямо сейчас, не обнаружены. Риски касаются того, что сбой будет невидим (OPS-1…4), медленного восстановления (OPS-5, OPS-6) и процесса поставки (OPS-8).

## Что сделано хорошо (не сломать при переделках)

- Блокировка `flock` на inode БД: второй экземпляр получает отказ (замер), блокировку снимает ядро при SIGKILL.
- Запуск быстрый и дешёвый: десятки мс, ~18 МиБ RSS, CPU 0 в простое; ограниченный `http.Transport` (512 соединений на хост, таймауты dial/TLS/headers).
- Drain учитывает hijacked WebSocket и финализаторы учёта (`runtime.go:230-240`), SQLite не закрывается под работающим финализатором.
- `Pdeathsig` корректно привязан к потоку (`update_host.go:99-103`): после SIGKILL launcher worker выходит за 15 мс.
- Загрузки релизов ограничены по размеру и времени, разрешены только хосты GitHub по HTTPS; запись `state.json` атомарная с fsync; версии хранятся по sha256; staging очищается под lock.
- Go-бинарь воспроизводим бит-в-бит; buildinfo содержит `vcs.revision`.
- Ошибки, видимые клиенту, не содержат секретов. Это правильный принцип, но сейчас он применён слишком широко и скрывает причины (OPS-4).

## Ограничения аудита

- Hardened-юнит проверен только `systemd-analyze security --offline`. Реальный запуск под systemd с seccomp не выполнялся (юниты ставить запрещено).
- Сквозное самообновление (скачивание и переключение) не воспроизводилось: источник жёстко привязан к GitHub. Оценки простоя и окна WaitForIdle — по коду, это гипотезы.
- Поведение при панике в фоновых циклах выведено из кода (нет `recover`), не воспроизводилось.
- Размер и нагрузка прод-БД неизвестны: оценки бэкапа и `VACUUM INTO` даны на синтетике (C-sqlite3, NVMe).
