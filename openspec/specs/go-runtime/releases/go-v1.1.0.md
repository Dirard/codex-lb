# Go v1.1.0 — быстрее, надёжнее, наблюдаемее; размер под сервер, бэкапы и защита админки

## Перед обновлением прочитайте

- **Проверка API-ключей.** Если в настройках проверка ключей выключена, раньше запросы через reverse proxy на том же хосте считались «локальными» и проходили без ключа. Теперь доступ без ключа есть только у сетей из `--unauthenticated-client`, а клиент определяется через `--trusted-proxy`. Клиентам нужен действующий API-ключ, либо добавьте нужную сеть явно.
- **Повторный вход.** Формат сессии админки сменился: после обновления все входят заново. Сессии отчётов по ключу продолжают работать.
- **TOTP.** Если TOTP настроен, код теперь спрашивается при каждом входе.
- **Reverse proxy.** Рекомендуется запускать с `--trusted-proxy 127.0.0.1/32 --trusted-proxy ::1/128` и `--public-origin https://ваш-домен`, а прокси должен передавать `X-Forwarded-For` и `X-Forwarded-Proto`. Шаблон `deploy/codex-lb.service` обновлён.
- **Model sources на приватных адресах** (self-hosted) требуют `--allow-private-model-sources`.

## Размер под сервер

- Лимиты больше не зашиты под 1 vCPU / 1 ГБ. При старте определяются CPU, доступная память (с учётом `MemoryMax` systemd и лимитов контейнера) и лимит дескрипторов. Из них выводятся одновременные генерации, очередь, WebSocket-клиенты, upstream-сессии и соединения, пул читателей SQLite и мягкий лимит памяти Go (75 %).
- На хосте класса 1 ГБ лимиты прежние: 512 / 128 / 4096. На 4 ГБ — 2048 генераций, очередь 512, 16384 клиента и 16 читателей на 6 CPU.
- Переопределение: `--memory-limit auto|off|3GiB`, `--max-generations`, `--max-client-websockets`; `GOMEMLIMIT` соблюдается. Обнаруженные ресурсы, лимиты и текущая загрузка видны в **Settings → Runtime capacity** и в `GET /api/runtime/capacity`.

## Скорость

- Число синхронных записей SQLite на запрос сокращено с 6 до 2: резерв и affinity — одна запись до отправки, settlement, outcome и continuation — одна после ответа. fsync на запрос при параллельной нагрузке: 3,5 → 0,55. Задержка до отправки при 8 параллельных запросах с контекстом 256 KiB: 42 → 20 мс.
- Меньше разборов тела запроса и событий: подготовка запроса на 1 MiB — около 10 вместо 22–27 мс, обработка SSE-события 3,6 → 1,2 µs, запись события клиенту 820 → 31 ns.
- Отчёты за 30 дней строятся за 0,75 вместо 3,1 с; обзор дашборда работает и при 500 аккаунтах (раньше падал от ~139). Глубокие страницы логов — keyset-курсор.
- Дашборд: первая загрузка 1921 → 357 КБ (статика сжата заранее br/gzip, JSON админки сжимается, языки и графики грузятся по требованию).

## Надёжность

- Пул upstream WebSocket: кадр, пришедший на простаивающий сокет, больше не попадает в следующий ответ; медленный клиент не убивает здоровый ответ проверкой живости; простаивавший сокет проверяется ping до отправки; завершение ответа больше не закрывает сокет владельца из-за отменённого ping.
- HTTP/2 ping к провайдеру, кэш TLS-сессий, повторное использование HTTP/1.1-соединений; стриминг tool-call для chat-источников; heartbeat для нативного SSE Codex.
- При quota failover запрос с серверным `conversation` больше не отправляется на другой аккаунт без контекста; compact replay сохраняет Lite-флаг.
- Длинная переоценка цен больше не блокирует учёт запросов на 5+ секунд.

## Эксплуатация и наблюдаемость

- У каждого запроса `X-Request-Id` и строка JSON-журнала при ошибке (успешные — на уровне debug, `--log-level`); фоновые ошибки и паники журналируются без утечки данных; сводки старта и остановки.
- `--metrics-listen 127.0.0.1:9464` включает Prometheus-метрики и pprof на отдельном порту; на основном порту `/metrics` и `/debug` теперь 404.
- Замена бинарника на старую версию (аварийный даунгрейд) больше не игнорируется.
- Обновления с миграцией базы ставятся из админки (начиная с go-v1.0.11); при неудачном старте восстанавливается резервная копия.
- Шаблон systemd усилен (`systemd-analyze security` 8.3 → 1.4), бесконечные перезапуски с паузой, `LimitNOFILE=65536`; Docker запускается без самообновления.

## Данные и резервные копии

- **Бэкапы.** Онлайн-снимок раз в сутки (по умолчанию хранится 3) в `<data-dir>/backups/` с проверкой целостности; ручной запуск и скачивание в **Settings → Backups**, CLI `codex-lb backup --data-dir … --output …`. `encryption.key` в снимок не входит — храните его отдельно.
- Ретенция догоняет рост; история квот по умолчанию 45 дней с прореживанием; урегулированные резервы чистятся; WAL ограничен 64 МиБ и регулярно сбрасывается; `PRAGMA optimize` раз в сутки. Финансовые записи (`usage_events`) по умолчанию не удаляются.

## Безопасность

- Первичная настройка админки всегда требует одноразовый bootstrap-токен: из `CODEX_LB_DASHBOARD_BOOTSTRAP_TOKEN` (не короче 32 символов) или из файла `<data-dir>/dashboard-bootstrap-token`, путь к которому пишется в журнал.
- Отзыв сессий («выйти везде»), выход после 12 часов бездействия, срок жизни сессии не больше 30 дней; лимиты попыток входа на клиента и на установку; bcrypt вне общей блокировки.
- Защита model sources от обращений к внутренним адресам; CSP, HSTS при `--public-origin`, cookie `__Host-` и `SameSite=Strict`; повторный ввод пароля для экспорта токенов и применения обновления.
- Подготовлена проверка подписи релизов (включится, когда в бинарник будет встроен ключ).

## Обновление

Схема SQLite **33 → 40**, протокол обновления **1**. Обновитесь сначала до **go-v1.0.11** (та же схема), затем до go-v1.1.0 через **Settings → Runtime updates**: перед переключением делается резервная копия, при неудачном старте она восстанавливается автоматически. После обновления откат через админку на 1.0.x недоступен — для возврата нужна эта резервная копия и старый бинарник. При ручной замене бинарника сделайте копию каталога данных и `encryption.key`.

Архивы Linux amd64/arm64 содержат статический `codex-lb` со встроенной админкой, лицензии и шаблон systemd. Проверьте `SHA256SUMS`; `./codex-lb version` должен показать `go-v1.1.0`.

## Проверки и ограничения

Прошли `go vet`, `golangci-lint`, полный `go test` и `go test -race`, `govulncheck`, 1277 тестов дашборда, lint и typecheck, контрактные тесты на собранном бинаре, `openspec validate`. Цифры скорости получены на локальных заглушках провайдера и могут отличаться на реальном VPS. Реальные провайдеры не использовались; усиленный юнит systemd проверен только `systemd-analyze`. Публикация релиза сама по себе не обновляет сервер.
