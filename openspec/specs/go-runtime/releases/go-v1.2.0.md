# Go v1.2.0 — обновления без простоя

## Перед обновлением прочитайте

Если вы обновляетесь с go-v1.0.x, в эту версию входят все изменения go-v1.1.0 и go-v1.1.1 (они выходили как pre-release). Подробности — в [заметках go-v1.1.0](https://github.com/Dirard/codex-lb/releases/tag/go-v1.1.0). Коротко:

- **API-ключи.** Запросы через reverse proxy на том же хосте больше не считаются «локальными». Без ключа пропускаются только сети из `--unauthenticated-client`, а клиент определяется через `--trusted-proxy`.
- **Повторный вход.** После обновления все входят в админку заново. Если TOTP настроен, код спрашивается при каждом входе.
- **Reverse proxy.** Запускайте с `--trusted-proxy 127.0.0.1/32 --trusted-proxy ::1/128 --public-origin https://ваш-домен`. Прокси должен передавать `X-Forwarded-For` и `X-Forwarded-Proto`.
- **Бэкапы.** Онлайн-снимки базы включены по умолчанию (раз в сутки, хранятся 3) в `<data-dir>/backups/`. `encryption.key` в снимок не входит.

## Обновления без простоя

- Обновление из **Settings → Runtime updates** больше не ждёт момента без запросов и не перезапускает сервер. Новая версия стартует рядом с текущей, проверяет базу и начинает принимать соединения на том же сокете. Текущая версия доводит до конца уже принятые запросы — стримы, очередь, текущий ход WebSocket, даже запросы на соединениях, которые она приняла, но ещё не дочитала, — и завершается. Ни одна попытка соединения не отклоняется, ни одна генерация не обрывается. Простаивающие keep-alive соединения старой версии закрываются: запрос, отправленный клиентом ровно в этот момент, увидит закрытое соединение. Это свойство HTTP/1.1, идемпотентные запросы клиенты повторяют сами.
- Простаивающие WebSocket-соединения Codex закрываются с кодом 1001, и клиент переподключается к новой версии. Активное соединение закрывается после завершения текущего ответа.
- Пока работают обе версии, каждая учитывает нагрузку другой: общий лимит генераций, лимиты аккаунтов, справедливую долю API-ключей и память. Фоновые задачи (автоматизации, опрос квот, ретенция, бэкапы, метрики) выполняет только одна версия.
- Предыдущей версии даётся до 30 минут на доработку принятых запросов, затем обычная остановка с `--shutdown-grace`.
- Если у релиза несовместимая миграция базы, обновление идёт по-старому: ждёт момента без активных запросов и коротко перезапускает сервер. Админка заранее показывает, какой способ сработает.
- Откат на предыдущую версию тоже бесшовный. После аддитивной миграции он не требует восстановления бэкапа.
- Лаунчер теперь держит порт и блокировку базы всё время работы сервиса. Даже при обычном переключении соединения ждут в очереди ядра, а не получают отказ.
- При старте лаунчер запускает вместо себя более новую установленную версию. Поэтому логика обновления сама обновляется из админки, начиная со следующего запуска. Если такой лаунчер не поднялся, при следующем старте это не повторяется, и сервис работает с установленным вручную бинарником.

## Память под тела запросов

- Тела запросов на всех маршрутах прокси (Responses по HTTP и WebSocket, Chat Completions, embeddings, compact, control, файлы, транскрипция, realtime, warm-up) теперь укладываются в один общий бюджет в байтах. Раньше считалось число запросов, а compact, нативные маршруты и транскрипция не ограничивались вовсе.
- По умолчанию бюджет — восьмая часть обнаруженной памяти (128 МиБ на хосте 1 ГБ, 512 МиБ на 4 ГБ). Один API-ключ может занять не больше половины. Переопределяется флагами `--body-memory-budget 1GiB` и `--body-memory-key-share 50`. Текущее заполнение видно в **Settings → Runtime capacity**.
- Байты списываются по мере прихода тела. Если тело не приходит 10 с, запрос получает 408. Слишком большое тело получает 413, а не повторяемый 503.
- Пока при обновлении работают обе версии, у каждой свой бюджет. В худшем случае на эти минуты он удваивается.

## Исправления

- Если два процесса одновременно обновляли OAuth-токен одного аккаунта, проигравший больше не выдаёт ошибку и не может пометить аккаунт как требующий повторного входа: он берёт токен, сохранённый победителем.
- Запись в SQLite из двух процессов не падает с `SQLITE_BUSY`: транзакции записи начинаются с `BEGIN IMMEDIATE`, а 5-секундный бюджет пакета записи отсчитывается после получения блокировки.
- Резервы usage-учёта помечаются как прерванные только для завершившихся процессов, а не для всех открытых резервов при каждом старте.

## Обновление

Схема SQLite **41** (аддитивная миграция: владелец резерва и нижняя граница совместимой схемы). Протокол обновления **1**, новый протокол передачи **1**.

**Один раз нужна ручная установка.** Логику обновления выполняет лаунчер, то есть бинарник, указанный в `ExecStart` юнита systemd. Обновления из админки его не заменяют. На версиях до go-v1.1.1 включительно бесшовное переключение и делегирование заработают только после того, как этот бинарник один раз заменят вручную:

1. Скачайте архив своей платформы и `SHA256SUMS`, проверьте контрольную сумму: `sha256sum -c SHA256SUMS --ignore-missing`.
2. Распакуйте и проверьте версию: `./codex-lb version` должен показать `go-v1.2.0`.
3. Установите поверх bootstrap (путь из `ExecStart`, например `/usr/local/bin/codex-lb`): `sudo install -m 0755 codex-lb /usr/local/bin/codex-lb`.
   Если юнит экспортирует `GOMEMLIMIT`, оставшийся от сервера поменьше, уберите его: иначе лимиты будут рассчитаны под этот лимит, а не под память хоста.
4. Перезапустите сервис: `sudo systemctl restart codex-lb`. Это единственный перезапуск: старая версия дорабатывает запросы в пределах `--shutdown-grace`, затем бэкап и миграция (на базе 1,3 ГБ: снимок около 17 с, миграция 33 → 41 около 8 с). Лаунчер примет новый бинарник, перед миграцией сделает резервную копию базы в `<data-dir>/updates/` и запустит go-v1.2.0. Прежняя версия останется в истории. Вернуться на версию со схемой старше 41 можно только через эту резервную копию.

Если первый старт новой версии сорвётся до того, как она начнёт принимать запросы, лаунчер сам восстановит бэкап этого запуска и вернёт прежнюю версию. Если бэкап не удался, база не мигрирует и сервис не стартует, пока бэкап не пройдёт.

- **go-v1.0.10 и старше:** обновление до go-v1.2.0 из админки невозможно. Релиз скачается и будет отклонён из-за другой схемы базы, поэтому нужна ручная установка выше.
- **go-v1.0.11 – go-v1.1.1:** обновление из админки работает, но по-старому, с ожиданием простоя и перезапуском. Бесшовными станут переключения после ручной замены bootstrap. Её можно сделать и после такого обновления — тем же бинарником go-v1.2.0, предыдущая версия сохранится.
- **Флаги.** Флаги в `ExecStart` разбирает bootstrap до того, как запустит более новую установленную версию. Добавляйте туда только флаги, которые понимает установленный вручную бинарник.

## Проверки и ограничения

Прошли `go vet`, `golangci-lint`, полный `go test` и `go test -race`, `govulncheck`, тесты дашборда, lint и typecheck, `openspec validate`. Интеграционные тесты на реальных бинарниках: обновление и откат под непрерывной нагрузкой без единого отказа, запрос, который продолжается во время переключения и завершается на старой версии, переходы между старым и новым протоколом в обе стороны, делегирование лаунчера и защита от его сбоя. Две базы на одном файле проверены конкурентной записью; без `BEGIN IMMEDIATE` этот тест падал. Миграция 33 → 41 отрепетирована на копии рабочей базы 1,3 ГБ. Реальные провайдеры не использовались. Docker по-прежнему запускается без самообновления. Публикация релиза сама по себе не обновляет сервер.
