# Go v1.14.0 — пул запросов на ключ

## Изменения

- У API-ключа появился пул запросов: не больше N запросов к моделям в минуту (от 1 до 10000) и максимальное ожидание свободного места (от 0 до 60 секунд, по умолчанию 30). Пул задаётся в редакторе ключа (**Request pool**) или через admin API: `PATCH /api/api-keys/{id}` с `{"requestPool":{"requestsPerMinute":120,"maxWaitSeconds":30}}`, а `"requestPool": null` его снимает. Изменение действует со следующего запроса, перезапуск не нужен. Ключи без пула работают как раньше.
- Место в пуле освобождается через 60 секунд после того, как его занял запрос. Запрос сверх пула ждёт своей очереди, если место освободится в пределах максимального ожидания. Иначе он сразу получает `429` с `Retry-After` (через сколько секунд освободится место) и телом OpenAI `{"error":{"type":"requests","code":"rate_limit_exceeded",...}}`. Codex читает из сообщения «Please try again in Ns.» задержку перед повтором. Клиент, отключившийся во время ожидания, место не занимает.
- В каждом ответе на запрос ключа с пулом есть заголовки `x-ratelimit-limit-requests` (размер пула), `x-ratelimit-remaining-requests` (сколько мест свободно сейчас) и `x-ratelimit-reset-requests` (через сколько освободятся все занятые места, например `42.5s`). Они есть и при ошибках, и в отказе `429`.
- Пул расходуют запросы к моделям: Responses по HTTP, каждый `response.create` в WebSocket Responses, compact, изображения, chat completions, embeddings, транскрипция, создание звонков Realtime и Live, сессии Realtime WebSocket, создание видео и `/v1/warmup`. Не расходуют: открытие WebSocket, `response.cancel`, sideband-сокеты, client secrets, статус и список видео, управляющие и файловые маршруты Codex, `/v1/models`, отчёты ключа и весь дашборд.
- В WebSocket Responses ответ на открытие соединения несёт заголовки пула. Отказ в ходе — кадр `{"type":"error","status":429,...,"headers":{...}}` с теми же значениями, соединение остаётся открытым. Пока ход ждёт места, Codex получает `codex.keepalive`.
- Страница ключа показывает его пул в свойствах.

## Обновление

Схема SQLite 50: в `api_keys` добавлены два необязательных столбца пула. Миграция аддитивная: предыдущая версия продолжает работать на той же базе во время обновления (в эту минуту пул не действует на её запросы). Протоколы обновления и передачи не меняются. С go-v1.2.0 – go-v1.13.2 обновление из **Settings → Runtime updates** проходит без простоя. Откат на go-v1.13.2 возможен без восстановления из резервной копии: старый код не читает новые столбцы.

## Проверки и ограничения

- Гейты: `go vet`, `golangci-lint`, `go test`, `go test -race`, `govulncheck`, `openspec validate`, тесты дашборда, сборка и контрактные тесты на собранном бинарнике.
- Ожидание, отказ, освобождение места при отключении клиента и смена пула без перезапуска проверены на маршрутах `/v1/responses` и `/backend-api/codex/responses` с управляемым временем (`testing/synctest`). Кадры WebSocket — на настоящем соединении. Проверено, что каждый перечисленный маршрут модели расходует пул в собранном runtime, а остальные маршруты его не трогают.
- Пулы хранятся в памяти процесса. Новый процесс после обновления начинает с пустыми пулами, поэтому в минуту обновления ключ может получить до двух объёмов пула.
- В журнале запросов время ожидания в пуле не отражается.
- Публикация релиза сама по себе не обновляет сервер.
