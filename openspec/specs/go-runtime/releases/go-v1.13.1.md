# Go v1.13.1 — балансировка голоса между аккаунтами

## Изменения

- Раньше все голосовые запросы шли на первый активный ChatGPT-аккаунт по порядку id: звонки GPT-Live, звонки Realtime (приложений и самого Codex) и WebSocket-сессии Realtime. Вся нагрузка ложилась на один аккаунт, а отказ по лимиту не переводил запрос на другой.
- Теперь голос выбирает аккаунт из доступных ключу. Порядок такой:
  1. сначала аккаунты без голосового предупреждения;
  2. затем аккаунты, у которых нет окна Codex, исчерпанного на 100%;
  3. затем аккаунты с наименьшим числом идущих звонков и сессий;
  4. затем с наименьшим использованием окон.

  Если разговор уже привязан к аккаунту, он на нём и остаётся.
- **Переключение.**
  - Если подписка отказала с HTTP 429 при создании звонка или при подключении сессии, пока ничего ещё не передано, запрос уходит на следующий аккаунт. Всего пробуется не больше трёх.
  - Отказавший аккаунт не получает голос в течение `Retry-After` из ответа, а если его нет — 15 минут.
  - Резерв на ключе берётся заново для каждой попытки, а у отказавшей возвращается.
  - Другие ошибки запрос не переносят: такая попытка могла уже выполниться.
- **Нет свободных аккаунтов.** Если все аккаунты остывают, запрос сразу получает 429 `voice_limit_reached` с `Retry-After`, ничего не резервируя.
- **Предупреждения подписки.** Если во время звонка GPT-Live подписка присылает `usage_limit.status` (например, `approaching`), аккаунт до `reset_seconds` (по умолчанию 15 минут) уходит в конец очереди для новых голосовых запросов. Текущий звонок продолжается.

## Обновление

Схема SQLite не меняется (49), протоколы обновления и передачи тоже. С go-v1.2.0 – go-v1.13.0 обновление из **Settings → Runtime updates** проходит без простоя. Счётчики, остывание и предупреждения хранятся в памяти воркера; после обновления они набираются заново.

## Проверки и ограничения

- Гейты прогнаны локально, а не в CI: `go vet`, `golangci-lint`, `go test`, `go test -race` (четыре шарда, как в CI), `govulncheck`, тесты дашборда, сборка, контрактные тесты и `openspec validate`.
- Тесты с двумя аккаунтами против локальной заглушки проверяют:
  - переход звонка Live, звонка Realtime и сессии Realtime на другой аккаунт при 429;
  - что при 502 запрос остаётся на своём аккаунте;
  - ответ с `Retry-After`, когда отказали все аккаунты;
  - распределение по нагрузке;
  - уход предупреждённого аккаунта в конец очереди.
- Как подписка отказывает при исчерпанном голосовом лимите, ни разу не наблюдалось. Предполагается 429, как у остальных её лимитов.
- Нагрузка звонков Realtime по WebRTC и звонков Codex не считается: их звук идёт мимо codex-lb.
- Релиз собран вручную и не подписан: ключ подписи есть только в CI.
- Публикация релиза сама по себе не обновляет сервер.
