# Переписать codex-lb на Go с выбранными возможностями

- Last edited with skill pack: `0.2.2`

## Title and scope

Сделать самостоятельный codex-lb на Go в текущем репозитории, сохранив выбранные пользователем возможности до переключения сервера. Старый код временно хранится в `legacy/`; исправления оцениваются по конкретным сбоям, а не по факту смены языка.

Одобрено пользователем: SDD, Go, чистая архитектура, один бинарник, собственное развитие, перенос текущего кода в `legacy/`, функциональный паритет за вычетом явно исключённых функций. Изменения в рабочем дереве входят в исходную версию, а не выбрасываются.

## Planning anchor

Входы старой версии: `app/main.py#create_app`, `app/modules/proxy/api.py#responses`, `responses_websocket`, `v1_responses` и `v1_responses_websocket`. Требуется заменить реализацию, а не сохранить внутреннюю структуру Python/Rust.

Базовый HEAD при обследовании: `003d3e501e4912e34be731e50f2d220e966b64eb`; поверх него присутствуют незакоммиченные изменения цен, групп и транспорта. HEAD без этих изменений не является полной исходной версией для переноса.

Действующие `openspec/specs/**` остаются описанием legacy. Для нового runtime вводится `go-runtime`; нормативные решения находятся в `specs/go-runtime/spec.md` этого change. Документы `specs/spec-lifecycle/` являются процессом, не функциями приложения.

## Connected groups or observed existing logic

- Вход и безопасность: proxy API, `request_policy.py`, dashboard auth и firewall проверяют ключи, модель, доступные аккаунты и источник IP. В Go эти проверки остаются до обращения к провайдеру; админка не становится публичной из-за удаления гостевого режима.
- Владение сессией: `LoadBalancer.select_account`, `continuity.py`, `affinity.py`, `replay_safety.py`, file pins и bridge coordinator связывают продолжение с аккаунтом. Удаление кластера позволяет убрать межрепличную пересылку, но не позволяет убрать привязку ответа, файла и голосового вызова к владельцу.
- Хранение: `app/db/models.py`, repositories, `ApiKeysService.finalize_usage_reservation` и request/report rollups связывают успешные и ошибочные попытки с лимитами и историей. Новая SQLite не пересчитывает накопленные суммы только из сохранившихся raw-логов.
- Секреты: старые proxy API keys сверяются через SHA-256 UTF-8 представления; OAuth-токены защищены Fernet с отдельным ключевым файлом. Перенос не требует раскрытия plain API keys, но не сможет расшифровать OAuth без корректного encryption key. Действующие сессии админки не переносятся как доверенные cookies.
- Транспорт: Python `native_egress.py` обменивается кадрами с Rust helper. Подтверждённый ранее сбой: burst более 64 событий мог переполнить очередь до запуска готового consumer. Это регрессионный случай для нового транспорта, не основание переносить subprocess-протокол.
- Админка: существующие `frontend/src/features/{accounts,account-groups,api-keys,reports,settings,auth,automations,firewall,sticky-sessions,model-sources}` пригодны для переноса интерфейса. Сборка React может требовать Node/Bun на машине сборки; серверный бинарник не должен требовать их для работы.
- Внешние API: отдельный локальный `/home/dirard/dev/ai-apps/codex-relay` написан на Rust, MIT. `codex-relay.service` активен и описан как мост Codex Responses к Z.AI Chat Completions. Источники поведения: `src/translate.rs`, `stream.rs`, `session.rs`, `quirks.rs`, `upstream_request.rs`, offline compatibility tests. Этот сервис и его настройки не изменяются при разработке codex-lb.
- Спецификации для повторного использования: `responses-api-compat`, `api-keys`, `account-groups`, `admin-auth`, `api-firewall`, `files-upload-protocol`, `realtime-api-compat`, `model-source-routing`, `automations`, `rate-limit-reset-credits`, `usage-refresh-policy`, `usage-error-metrics`, `data-retention` и `graceful-shutdown`. Текущие Go-independent требования проверяются, а внутренние Python/SQLAlchemy детали не копируются буквально.
- Исключённые возможности: `telemetry`, `replica-operations`, `bridge-ring-membership`, `quota-phase-planner`, гостевая часть `admin-auth`, PostgreSQL-часть `database-backends`, proxy-pool часть `upstream-proxy-routing`, публичные `/v1/images/*`, Helm/Nix/distroless поставка. Их legacy-описания сохраняются как история и не считаются контрактом нового продукта.
- Affinity slice: UI `web/src/features/settings/components/routing-settings.tsx` и `sticky-sessions/{api,schemas}.ts` уже показывают TTL, пороги и CRUD bindings. Go хранит только `stickyThreadsEnabled` без routing consumer; `response_ownership.go` разрешает hard continuation по previous/session, а `account_admission.go` атомарно выбирает доступный account. Legacy anchors — `affinity.py`, `sticky_repository.py`, `sticky_sessions/service.py`, `settings/repository.py`; нормативные typed/soft/admin/owner contracts из `sticky-session-operations` переиспользуются с Go-адаптацией ниже. Нужны общие settings/persistence, оба HTTP/WS ingress и compact, не отдельный UI-кэш. Legacy bridge/ring не переносится; reverse-documentation отдельным документом не нужна после этого точечного mapping.

## Use cases

### 1. Сохранить legacy и создать Go-корень
current repository --verify source and destinations--> move plan --relocate implementation without overwriting--> preserved legacy --initialize Go module--> Go development root

Implementation Logic:
- Перед переносом проверить существующие каталоги и изменения. Перемещать явный перечень путей без `reset`, `clean`, удаления и перезаписи существующего `legacy/`.
- `.git`, активные SDD/OpenSpec материалы и агентские инструкции остаются доступными. Историю лицензии и copyright сохраняем. Python/Rust/React исходники, старые сборки, CI и deployment-конфигурации сохраняются в legacy; не запускать старые release workflows из нового корня.
- Не включать реальные `.env`, ключи, базы, архивы запросов, `.venv`, `node_modules` и build cache в коммиты или Go assets. Перенос игнорируемых путей не должен сделать их отслеживаемыми; правила ignore проверяются до записи нового root build context.
- Clean architecture: `cmd/codex-lb` собирает зависимости; `internal/domain` содержит правила без SQL/HTTP; `internal/application` управляет сценариями и владеет нужными интерфейсами; `internal/adapters` реализует HTTP, SQLite и провайдеры. Не создавать универсальный plugin framework или интерфейсы для каждого helper.
- Go runtime не обращается к Python/Rust subprocess или локальному codex-relay. SQLite driver и WebSocket библиотека выбираются как реальные недостающие стандартной библиотеке возможности; криптография и HTTP используют существующие проверенные примитивы.

Tests:
- description: Перенесённые изменённые и неотслеживаемые файлы сохранились побайтно; секретные/сгенерированные пути остались ignored; `.git` не изменён переносом.
- description: `go test`, `go test -race`, сборка бинарника и запуск не требуют Python/Rust/Node на runtime-машине.

### 2. Принять запрос Codex и безопасно завершить его
client request --authenticate and validate scope--> admitted request --reserve key budget and resolve owner--> selected account --dispatch once--> active response --finalize outcome and release resources--> settled request

Implementation Logic:
- Сохранить HTTP/SSE и WebSocket Responses, compaction, модельный каталог, необходимые Codex control/conversation/file маршруты и клиентскую совместимость. Не подменять рабочий протокол набором ответов-заглушек.
- `compaction_trigger` допускается ровно один раз последним элементом верхнего уровня input; неправильная форма отклоняется до admission. Только HTTP Codex Responses переводит такой streaming-запрос в compact с теми же owner, key policy, capability lineage и единичным settlement; `/v1/responses` не переадресует его. Успешный HTTP Codex compact возвращает клиентский stream `created → output_item.added → output_item.done → completed` с encrypted compaction item и настоящим usage. Codex WebSocket сохраняет legacy forwarding валидированного `response.create` на subscription account, без HTTP compact synthesis или маршрутизации на external source.
- Standalone и trigger compact используют ту же фильтрацию каталога модели/тарифа, что и Responses, до reservation. Установленный conversation/file owner не заменяется другим только из-за несовместимости каталога; новый compact пропускает неподходящих кандидатов. Enforced tier нормализуется по той же политике каталога и попадает в фактический upstream body.
- Compact применяет общий `parseResponse` для model/tier/reasoning policy, предварительно удалив неподдерживаемые compact-поля. Поддерживаются оба разрешённых режима ключа: forced reasoning или список допустимых effort; глобальный запрет Fast Mode действует и поверх enforced tier. Строковый input превращается в обычный user item и проходит тот же budget/trim, что массив. Lite normalization не извлекает инструкции; owner resolution остаётся после trim. Дублирующая compact policy удаляется.
- Новый compact после получения общего admission использует тот же stateful `Proxy.selectAccount`, что Responses, ограниченный ChatGPT: price availability, routing strategy, purchased/monthly/additional quota и policy overrides не дублируются. Runtime явно подключает selector; неинициализированная конфигурация не заменяется выбором первого eligible аккаунта. Established conversation/file owner сохраняет прежнюю строгую привязку и каталог без telemetry gate. Compact проходит одну admission и один settlement; ancillary billed operations сохраняют свою admission через общий admitted accounting helper.
- `fill_first` сохраняет legacy-порядок: максимальный primary used %, затем secondary used % (unknown = 0), затем account ID по возрастанию. История last-selected не меняет этот deterministic tie-break. Manual policy, scope, quota/catalog gates и заданный earlier-reset bucket по-прежнему применяются до стратегии; established owner не проходит повторный выбор.
- `relative_availability` использует сохранённые `relativeAvailabilityPower` (finite > 0, default 2) и `relativeAvailabilityTopK` (целое 1–20, default 5), а не константы внутри selector. Существующий `/api/settings` сохраняет их с optimistic version check; legacy import сохраняет ненулевые валидные значения, миграция добавляет прежние defaults для старой Go-базы. При новом admission один settings snapshot задаёт эти параметры и для обычного Responses, и для compact; ограничения и owner continuity не меняются.
- `sequential_drain` ранжирует по configured long-window plan capacity, затем стабильному SHA-256 account ID, не по остатку quota или лексикографическому ID. `reset_drain` ранжирует по дню ближайшего будущего secondary reset (fallback primary), затем меньшим primary/long usage, точному reset и тому же стабильному tie-break. Их собственный порядок и round-robin не подменяется предварительным generic earlier-reset bucket. Manual burn/preserve priority остаётся общей согласно нормативному `account-routing`, даже для drain; eligibility/model/key/group gates остаются выше стратегии. При relative selection текущее время фиксируется один раз, чтобы score comparator был устойчивым.
- Владелец включает provider/account, key scope и нужные идентификаторы сессии. Продолжение активной сессии при 0% идёт прежнему владельцу до подтверждённой upstream quota ошибки; это не разрешение открывать новые сессии на исчерпанном аккаунте.
- Запрет/удаление аккаунта, отзыв ключа, изменение группы, неподходящие права на модель и утрата аутентификации не обходятся правилом продолжения при 0%.
- Отличать upstream quota exhausted, временный rate limit, локальную перегрузку и transport failure; одного HTTP 429 недостаточно для смены владельца активного разговора.
- При настоящем quota отказе переходить к подходящему аккаунту внутри разрешённой области только когда восстановлена достаточная история, нет account-bound файла и ещё не отправлены клиенту несовместимые события. Не переносить старые `previous_response_id`/turn-state на нового владельца.
- Если запрос уже мог выполниться, не обещать exactly-once выполнение upstream и не повторять вслепую. При отсутствии безопасного продолжения вернуть распознаваемую ошибку, не теряя и не выдумывая историю.
- Каждому запросу принадлежат ограниченная очередь, cancel/deadline, socket и release/settlement. DB-транзакции не удерживаются во время ожидания upstream. Медленный consumer изолирован от соседних потоков.
- Раздельно учитывать время в локальной очереди, connect, первый upstream event и последний upstream progress. SSE keepalive поддерживает downstream соединение, но не считается доказательством прогресса модели.
- Длительная работа модели сама по себе не доказывает поломку прокси: timeout policy учитывает реальный upstream progress и отдельные budgets, без обещания убрать все долгие ответы. Успешный более поздний ответ не должен блокироваться устаревшим quota/cooldown состоянием от предыдущей попытки.
- Не объявлять оборванный/decode-failed ответ успешным; передавать сжатие, фреймы, UTF-8 и terminal events согласованно. При отмене освобождать capacity и завершать локальные записи ровно один раз.
- Восстановление после quota/rate-limit блокировки использует свежий usage snapshot с подтверждённым переходом истёкшего окна в новое доступное, а не платную пробу. Перед fetch сохраняются предыдущие окна и версия последнего provider outcome; узкая DB-запись возвращает только quota-derived статус в active при неизменившейся версии. Пауза, отзыв доступа и новый quota refusal не перезаписываются. Нулевой остаток активного владельца не превращается в локальную блокировку.

Tests:
- description: Воспроизвести потерянный предыдущий ответ, два аккаунта с quota failover, 0% без upstream ошибки, tool-output-only delta, file pin и ошибку после видимого tool call.
- description: Burst событий, медленный клиент, reset/timeout, ошибочное сжатие, отмена во время refresh и ожидания capacity не блокируют соседний запрос и не оставляют lease/reservation.
- description: Последовательность quota/error-события и успешного продолжения не оставляет старую ошибку бесконечным локальным запретом; несовместимые по времени результаты не перезаписывают более новое состояние аккаунта.
- description: Проверять протокол на offline upstream stubs и актуальных клиентских fixtures; production replay и платные model calls не запускать без отдельного согласования.

### 2.1. Уместить большую историю в compact без потери обязательного состояния
validated compact input --index state anchors and typed tool occurrences--> required and optional context --select budget-fitting history--> prepared input --resolve retained file owners and reserve usage--> upstream compact

Observed Existing Logic:
- Anchor: `CompactWithOptions` и `compactTriggerBody`. Legacy `requests.py#_trim_compact_input_for_upstream` сначала сохраняет необрезанные выбранные элементы, затем при необходимости заменяет уже наблюдавшиеся inline images только в обязательных tool outputs. Go пока делал image elision первым и отклонял оставшийся большой контекст.
- Связанные поверхности: оба HTTP compact входа; `prepareCompact`; поиск file owner после преобразования; общий каталог модели/тарифа; upstream body и ошибка 400 до reservation; клиентский SSE trigger result. Админка и схема БД этим преобразованием не меняются.
- `responses-api-compat` остаётся legacy baseline; требования Lite prelude, typed call pairing и приоритетных historical side effects повторно используются. Уточняется текущий `go-runtime`, legacy spec не переписывается.

Implementation Logic:
- Единый подготовительный путь применяется к standalone и trigger compact. Вмещающийся массив не меняется. Промежуточные данные — исходные `json.RawMessage`, оценка размера каждого элемента и индексы по `(call_id, protocol variant)` с порядком отдельных occurrences; это request-local данные, не новая история или cache.
- Обязательны system/developer directives, `additional_tools`, plan/goal state и связанные outputs. Последний обычный item, непарный последний call, side-effecting tail и anchored output без совместимого неиспользованного call сохраняются. Terminal trigger остаётся последним. Function/custom/apply-patch варианты и повторные call IDs не смешиваются.
- Полные исторические side-effect pairs получают ограниченный приоритет перед обычным head/tail; если они не помещаются вместе с обязательным состоянием, удаляются целиком. Неверифицируемый historical side-effect call без `call_id` не отправляется как сохранённая пара. Бюджеты legacy — 100000 estimated tokens всего и 12000 для обычного prefix.
- Выбор сохраняет исходный порядок и raw содержимое оставленных элементов. Пропуски отмечаются сообщением с числом items и оценкой tokens. Если marker framing выводит результат за предел, optional context удаляется с согласованием пар без повторного добавления удалённой половины. Проверяется фактический сериализованный input, включая framing и Unicode escaping.
- Только если выбор неизменённых элементов не помещается, допускается существующий image-elision helper для обязательных function/custom/apply-patch outputs. Последняя непронаблюдавшаяся user image или hosted computer screenshot не подменяется текстом. Если обязательное состояние всё равно не помещается — 400 до выбора аккаунта/ledger. File IDs из уже удалённой optional истории не влияют на owner.

### 2.2. Передать Responses Lite без доверия к клиентскому маркеру
normalized request --derive Lite mode from body or accepted continuation--> scoped Lite request --validate enforced model and prepare actual wire--> upstream request --expose accepted response id--> updated connection continuity

Observed Existing Logic:
- Legacy `requests.py#responses_input_uses_lite_tools`, `proxy.py#_normalize_responses_lite_websocket_client_metadata`, `request_policy.py#apply_api_key_enforcement` и `websocket/helpers.py#_record_websocket_responses_lite_acceptance` реализуют контракт `responses-api-compat` 2490–2644. Отдельная reverse-documentation не требуется: контракт и узкое чтение согласованы.
- Go `parseResponse → filterCatalogAccounts → Proxy.Respond → provider.callChatGPT` сохраняет input, но пока не выводит Lite mode. `httpapi.websocket` последовательно обслуживает запросы соединения; `responseOutput` скрывает prelude неуспешной попытки. `replayBody` отвергает `additional_tools`. Compact имеет отдельный provider entrypoint с тем же wire-контрактом. Админка и БД не меняются.

Implementation Logic:
- Источник Lite — `additional_tools` в input. Входной HTTP Lite header не пересылается. Reserved metadata key удаляется без учёта регистра; остальные client metadata и весь Lite input/instructions сохраняются. Некорректный объект metadata отклоняется до dispatch.
- Для прямого downstream WebSocket хранится одна пара effective model/последний принятый Lite response ID на соединение. Marker-only продолжение доверенное только при canonical true marker, совпадении модели после key enforcement/alias comparison и точном `previous_response_id`. Подготовка, отказ и принятие non-Lite запроса состояние не меняют. Запись выполняется при выдаче `response.created`, не по terminal completion; скрытый prelude попытки не создаёт доверенный ID. Состояние не разделяется между соединениями/ключами.
- На фактическом ChatGPT HTTP wire Lite даёт canonical header, на WebSocket — canonical marker только внутри `response.create`, никогда в handshake; `reasoning.context` становится `all_turns`. HTTP/compact выводят сигнал только из собственного input. External sources не получают привилегированный marker/header.
- Key-enforced модель с явно подтверждённым `use_responses_lite=false` отклоняется до reservation; отсутствие capability metadata не считается false. Общий catalog gate обслуживает Responses и compact.
- При fresh replay убираются previous/turn state и унаследованный marker. Режим вычисляется заново по реально восстановленному input. Account-neutral `additional_tools` и developer directives сохраняются; answered function/custom/apply-patch exchanges проверяются по типу и occurrence. Account-bound/opaque/unanswered history по-прежнему запрещает смену владельца.

### 2.3. Повторить compact после подтверждённого quota-отказа
admitted compact --dispatch and settle one attempt--> classified outcome --verify complete account-neutral input after quota refusal--> replayable compact --select a permitted untried subscription and clear owner anchors--> next compact attempt

Observed Existing Logic:
- Legacy `compact.py#_compact_account_neutral_replay_payload` проверяет неизменность подготовленного input, нейтральность и сохранённый assistant output перед новым input; `compact_responses` исключает отказавший аккаунт. Этот контракт повторно используется, но одного RATE_LIMITED статуса в Go недостаточно: выбранное пользователем правило требует реального quota refusal.
- Go `CompactWithOptions → billedAdmitted → provider.Compact` уже выбирает корректный аккаунт и завершает ledger до health write, но возвращает quota-ошибку без переключения. `Proxy` хранит зашифрованный полный operational context и общий безопасный `replayBody`; его cipher и selector подключаются явно к compact, без второго хранилища.

Implementation Logic:
- Одна общая capacity lease покрывает весь compact; каждая действительно отправленная попытка имеет собственные reservation/settlement. Только классифицированный upstream quota refusal разрешает следующий аккаунт. Ошибка settlement/health, generic 429, auth/transport/decode failure, отмена и ошибки локальных лимитов останавливают повтор. Общий deadline не расширяется отдельными upstream попытками; отказавшие IDs исключаются.
- После settled quota refusal сохраняется отказ у исходного continuation в key scope. При новом вызове уже подтверждённый флаг допускает ту же проверку replay без повторного запроса к исчерпанному владельцу. Пауза, удаление, изменение разрешённой группы или потеря доступа владельца не превращаются в quota proof; его scope проверяется до замены.
- Запись quota-флага сверяет key/response/account и rowid завершённой failed reservation этой попытки. Если session уже сохранена более новой reservation на том же account, старый отказ не меняет её quota-флаг; текущая generation по-прежнему допускает quota failover. Незавершённая либо принадлежащая другому key/account reservation недопустима. Общий метод вызывается обычным Responses и compact после settlement; используется существующий `reservation_rowid`, без новой схемы.
- Replay проверяется по фактическому подготовленному input. File/compaction/container/vector-store pins и непрозрачные conversation/prompt handles запрещают перенос. Терминальный validated trigger отделяется только для анализа истории и возвращается ровно один раз на wire. Известные provider item IDs удаляются; reasoning cache не переносится. Предыдущий response ID, turn state и transport affinity не уходят новому аккаунту.
- Для anchored continuation с доступной полной durable history используются исходные сообщения и outputs. Полный resend распознаётся по нормализованному prefix, чтобы не удваивать историю; однозначная input delta дополняется сохранённым контекстом. Нельзя выдавать укороченную/неоднозначную историю за полный prefix. Если durable history недоступна, допускается только неизменённый, self-contained authoritative resend с prior assistant output и последующим новым input; validated trigger может быть завершающим запросом на сжатие. Новая compaction без owner anchor использует собственный нейтральный input. После реконструкции input обязан помещаться без нового удаления контекста.
- При успешном повторе отчёт и новый response/session owner относятся к выбранному аккаунту. Внутренний quota-отказ не выходит в standalone JSON или synthesized trigger SSE; неподтверждённые расходы/потеря контекста не маскируются успехом. UI и схема БД этим slice не меняются.

### 2.4. Сохранить неизвестный расход обычного Responses
reserved Responses attempt --dispatch and retain available provider usage--> outcome with explicit accounting certainty --settle confirmed usage or retain reconciliation ownership--> accounted terminal response

Observed Existing Logic:
Native Chat/embeddings и ancillary operations уже используют `operationUsageUncertain`/`retainUncertainUsage`. Обычный `Proxy.settle` пока получает только числовой Usage без признака известности, а `provider.call` теряет result при error. Поэтому transport failure или отсутствующее usage может стать нулевым завершённым событием. SSE/WS parsers также должны сохранить подтверждённые counters, если после них отказывает delivery.

Implementation Logic:
- Через существующие upstream Result и application ResponseResult передаётся явная известность валидного usage. Missing/partial/invalid/overflow counters не равны explicit zero. Подтверждённые usage на failed/incomplete response либо до последующей ошибки не отбрасываются.
- Общий classifier/retained reservation path применяется в обычном Proxy до account outcome и continuation writes. Dispatched transport/timeout/cancel/panic, ambiguous 408/5xx и непригодный pricing не завершаются invented zero; budget остаётся held и pending row видна в журнале. Локальный preflight и доказанный небиллируемый refusal могут завершиться нулевым событием. Настоящий quota refusal сохраняет существующий безопасный failover после settlement.
- Классификация quota refusal не зависит от возможности replay. Подтверждённый отказ с billed usage либо видимым output не повторяется автоматически, но после durable accounting decision сохраняет quota-derived account/owner state. Для unknown usage такой decision — сохранённый `needs_reconciliation` с удержанным резервом; он не разрешает healthy-success outcome. Все outcome/owner записи сохраняют key/account/sequence fences. Даже подтверждённый `previous_response_not_found` с ненулевым usage не разрешает повторное списание через hydration.
- То же правило no second bill относится к compact: после settled quota refusal с ненулевыми token counters account/owner quota proof сохраняется, но standalone/trigger compact возвращает исходный отказ без повторного платного compact на альтернативе. Partial/invalid billing удерживает резерв, сохраняет независимо разобранный quota proof и также запрещает replay; общая ancillary accounting функция не подменяет uncertainty нулём из-за самого наличия quota error.
- Известность billing определяется явными валидными input/output counters, а не наличием избыточного total counter: отсутствующий total можно вычислить как сумму; присутствующий total и detail counters должны быть согласованы. `401` с подтверждённым ненулевым usage не повторяется скрыто при refresh токена; достоверный нулевой отказ остаётся допустимым для прежнего однократного same-account auth retry.
- Наличие billing report передаётся отдельно от его валидности: partial/invalid usage не равен отсутствующему usage даже в quota, missing-previous или authentication refusal. Такой report удерживает резерв и запрещает автоматический replay/refresh retry. Независимо декодированный quota error сохраняет account/owner proof даже при непригодных counters; повреждение billing не должно стирать этот отказ.
- Прямой native Chat (JSON/SSE) и embeddings сохраняют usage на отказах: HTTP rejection и error chunk сначала разбирают имеющиеся counters, затем возвращают error. Partial/invalid reported billing удерживает существующий резерв, включая HTTP 4xx, вместо fake zero; известность не восстанавливается одной проверкой наличия полей после ошибки декодирования. Непригодный новый billing report делает прежние stream counters неполным итогом, в отличие от простой ошибки доставки после подтверждённых counters. Общий ancillary auth retry запрещён при billed или непригодном reported usage/duration; `401` без billing либо с достоверными нулевыми token counters (без duration report) остаётся допустимым для одного refresh.
- Отсутствующий usage на nominal success по умолчанию даёт sanitized error, не terminal success. Явный source missing-usage opt-in сохраняет разрешённый ответ только для неметрируемого ключа, но не создаёт fake finalized usage/outcome; token/cost limits нельзя обходить. Уже видимый output не повторяется из-за uncertainty. Admission и transport resources освобождаются независимо от retained accounting.
- Не добавлять новую ledger/schema или отдельный background retry. Использовать существующие helper, durable reconciliation flag и CLI repair; исходное request ownership и диагностический error archive сохраняются.

- description: Реальные локальные HTTP/SSE/WS Responses и translated Chat fixtures проверяют explicit zero, missing/partial/invalid usage, charged terminal error, delivery failure после known usage, generic 429 против actual quota refusal, 408/503, disconnect/cancel/panic и held key limits.
- description: Missing-usage opt-in не обходит metered key, pending request-log не выдаёт invented zero, а успешный подтверждённый usage/continuation и существующие quota failover regressions не меняются.

### 2.5. Ограничить параллельную нагрузку на subscription аккаунты
validated scoped candidates --atomically choose and acquire account capacity--> owned account lease --observe first upstream event--> stream-only lease --complete or cancel attempt--> released account capacity

Implementation Logic:
- Реализовать `proxyAccountResponseCreateLimit`, `proxyAccountStreamLimit`, `proxyAccountStreamRecoveryReserve`, `proxyApiKeyFairShareCongestionThresholdPct` с legacy defaults `4/8/1/0`, текущими env aliases и tri-state overrides: отсутствующее поле сохраняет override, `null` наследует env/default, число `0` явно выключает соответствующий cap/fair-share. Первый settings row сохраняет startup env как overrides; upgrade прежней Go схемы получает nullable/inherit значения, legacy import сохраняет исходный выбор. GET показывает effective/override/env значения, PUT валидирует границы и version; restart/import сохраняют пользовательский выбор.
- Лимитер локален одному Go process, как уже согласовано для SQLite/single-instance поставки, не объявляется cluster-wide. Один mutex защищает живые account/key/waiting counts; selection и commit lease атомарны, сеть и SQLite I/O не выполняются под этим mutex. Состояние удаляется по release/cancel; не переносить Python bridge/ring, distributed leases или stale-reclaim workers.
- Create lease удерживается до первого upstream response event либо завершения попытки; stream lease — до возврата provider call. Каждый retry получает и освобождает собственную account lease, не теряя outer global admission. Исключения, panic, context cancellation и ошибки записи не оставляют slots занятыми.
- В Go нет отдельного Python reattach-stage. Recovery reserve сохраняет пользовательский смысл защиты работающего треда: им могут пользоваться только запросы с подтверждённым key-scoped conversation/file owner, включая HTTP continuation. Новый запрос, произвольный client header и synthetic warmup не получают этот приоритет. Normal work ограничивается `max(1,streamLimit-reserve)`, hard-owner work — полным stream cap; значение stream cap `0` отключает оба stream ограничения.
- Capacity нельзя использовать как quota proof или повод переносить активный hard owner. Новый мягко привязанный запрос выбирает свободного разрешённого кандидата; существующий owner ограниченно ждёт только свой аккаунт. При исчерпании bounded wait вернуть отдельную локальную 429/rate-limit ошибку и Retry-After для HTTP, без upstream health/quota mutation. SSE keepalive не фиксирует `200` до первого допущенного/reserved provider dispatch; после dispatch ожидание upstream по-прежнему поддерживается keepalive. Это относится и к Codex compact trigger. После уже переданных событий ошибки остаются SSE frames по прежнему контракту. Клиент не должен получать invented upstream quota error.
- При enabled fair-share congestion threshold конкурентный ключ учитывается лишь в его реально разрешённом model/account pool. Учитывать ожидающие запросы, чтобы активный ключ не захватывал каждый освобождённый slot перед конкурентом. Отмена удаляет waiting demand; режим `0` сохраняет отсутствие fairness restrictions. Алгоритм/границы соответствуют назначению существующей настройки, без внешнего scheduler.
- Обязательные callers: Proxy Responses HTTP/SSE/WebSocket (включая nonstream client с внутренним stream), standalone/trigger compact и public warmup через общий billed path, admin/scheduled WarmupService. External model sources/native Chat/embeddings сохраняют отдельный existing source MaxConcurrency; ChatGPT caps к ним не применяются.

### 2.6. Управлять мягкой привязкой новых запросов
unowned scoped request --classify key scoped locality hint--> typed affinity lookup --apply eligible preference and atomic capacity selection--> admitted account --compare and persist soft binding before dispatch--> routed request

Implementation Logic:
- Сохранить рабочие `openaiCacheAffinityMaxAgeSeconds` (positive integer, default1800), `stickyReallocationPrimaryBudgetThresholdPct`/`stickyReallocationSecondaryBudgetThresholdPct` (finite0..100, defaults95/100). Legacy `stickyReallocationBudgetThresholdPct` остаётся alias primary: явно заданный canonical primary выигрывает. GET/PUT/CAS/restart/import используют один источник. Новый settings row закрепляет startup TTL env `CODEX_LB_OPENAI_CACHE_AFFINITY_MAX_AGE_SECONDS`; текущая БД получает migration default. Не вводить runtime bridge knobs снятой Python архитектуры.
- Привязка — только предпочтение для request без уже разрешённого previous/session/turn/file owner. Hard owner никогда не читает, не перезаписывает и не удаляет soft mapping. `stickyThreadsEnabled` управляет автоматической thread/derived locality; явный `prompt_cache_key` остаётся самостоятельной cache hint. Hint не разрешает cross-account replay и не превращает account-scoped body в переносимый.

Thread hint получает domain-separated hash API key + process/thread tuple; явно переданный cache key получает hash API key + kind + value. Без явного hint автоматическая affinity использует bounded model/instructions/first-user fingerprint, не сохраняет prompt text и не путает API keys. Provider-facing cache hint не переписывается из thread identity и не пересылается чужому провайдеру как privileged Codex metadata.
- Хранить typed `prompt_cache`, `sticky_thread`, `codex_session` soft bindings отдельно от correctness ownership. У записи есть непрозрачный стабильный key, key scope, account, created/updated timestamps и version. Prompt-cache age считается от updated time с текущим TTL; durable locality kinds не очищаются TTL. Таблица/namespace не предоставляет право доступа к аккаунту: current key/group/model/capability/egress policy повторно фильтрует кандидатов перед использованием.

Нет mapping — sticky thresholds не вводят дополнительный admission ban. Capacity не закрепляет отказ на мягком pin: существующий account limiter выбирает свободную альтернативу атомарно.

Непригодная/истёкшая мягкая запись не авторизует hard continuation. Background cleanup переиспользует существующий bounded maintenance lifecycle, не новый scheduler.
- Сохранить authenticated `/api/sticky-sessions` list/filter/sort/page, single DELETE, batch delete до500 unique pairs, delete-filtered и stale purge со схемами существующего UI. Admin writes требуют прежний CSRF/auth. Список и totals читаются согласованно, key/account search literal, sort allowlisted. Purge удаляет только stale prompt-cache hints. Управление affinity не удаляет response/file/voice/capability ownership, поэтому очистка кэша не переносит активный тред.
- Legacy настройки импортируются. Старые global/unscoped hints нельзя объявить key-scoped ownership нового runtime: они сохраняются в уже существующем полном private source sidecar, но не активируются для произвольного ключа. Новые hints строятся из новых авторизованных запросов. Это не удаляет исходные данные и не переносит живые legacy sockets.

### 2.7. Отделить логический тред и turn-state ownership от мягкой affinity
validated identity sources --resolve independently scoped hard aliases--> consistent owner or explicit continuity refusal --dispatch on proven owner--> successful settled response --fence logical thread and turn aliases--> retained hard continuity

Implementation Logic:
- Когда присутствует Thread-Id, logical-session alias вычисляется из process/thread tuple, а не только process Session_id. Отсутствующий Thread-Id сохраняет прежний bare-session contract; наличие process session не делает соседний новый thread активным продолжением. Явный previous-response owner имеет приоритет над soft locality, но конфликт независимо доказанных hard owners не игнорируется.
- Незнакомый explicit X-Codex-Turn-State без другого доказанного hard owner возвращает409 до dispatch. Известный turn alias проверяется независимо от previous/session/file и не может указывать другому аккаунту. При known previous/session owner ранее не виденный opaque upstream token может пройти только к этому owner; durable alias появляется лишь после успешного accounted ответа. Generic failure не создаёт нового owner.
- WebSocket ingress отличает свой synthesized downstream token от client-supplied token внутренним флагом, не доверяет строковому prefix. Первый synthesized token ещё не доказывает owner; успешный settled response сохраняет его key-scoped alias. При reconnect такой token восстанавливает owner. Proxy-generated turn token никогда не передаётся upstream как его собственный непрозрачный token.
- Использовать существующее fenced continuation storage/TTL/bounds для typed aliases с source discriminator, не новую session engine. Quota-only verified failover и stale completion fencing сохраняются; новая запись одного логического треда не меняет соседний и не понижает capability lineage. HTTP, compact и direct WS используют один resolver, новые namespace prefixes нельзя записать как provider response ID.

- `ModelCatalogSelectionResult` сейчас не передаёт `prefer_websockets`, хотя subscription metadata его содержит. `upstream/websocket_sessions.go` знает HTTP handshake rejection до записи `response.create`; после adapter mapping это доказательство теряется. `provider/chatgpt_request.go` нормализует Lite по выбранному транспорту, поэтому HTTP fallback должен заново нормализовать исходный body, не переслать WS wire shape вслепую.

Implementation Logic:
- Выделить общий request-local selector. Downstream WebSocket сохраняет свой native subscription upstream WS путь, HTTP policy его не меняет; внешние источники остаются в своём поддерживаемом protocol/transport. Для HTTP explicit `upstreamStreamTransport=http|websocket` выигрывает; default/auto использует subscription catalog preference или явный Codex transport signal. Не считать данные внешнего model source subscription catalog. Неподтверждённый auto preference остаётся HTTP.
- В auto/default oversized body больше14MiB (существующий16MiB event/frame budget минус2MiB envelope), input image или hosted image generation используют HTTP; не вводить новый knob. Native Codex HTTP определяется по прежним User-Agent prefixes или Originator allowlist и не повышается обратно в WS по sticky headers. Эта классификация не даёт прав доступа и не выводится из одного только Session_id/turn-state.
- Для остальных HTTP requests effective policy берётся из key override, иначе из global settings. `always_http` и `pinned` выбирают HTTP; `always_websocket` сохраняет пригодный auto WS; `smart` сохраняет WS только при explicit previous/cache/session/thread/turn hint, а не при вычисленной мягкой fingerprint affinity. Выбор транспорта не меняет account owner, reservations, key/group/model/security rules или quota-only account replay.
- Сохранить существующий `responses-api-compat` контракт request-local metadata: четыре nonblank headers `x-codex-turn-metadata`, `x-openai-subagent`, `x-codex-parent-thread-id`, `x-codex-window-id` проходят явный allowlist в subscription adapter. HTTP сохраняет их как headers, WS проецирует в каждый `response.create.client_metadata`, включая reuse socket. Уже вычисленный provider-ом scoped `Session_id` также проходит транспортный allowlist; это не разрешение копировать произвольные клиентские session/authorization headers. Значения body с тем же ключом выигрывают, header matching case-insensitive; произвольные клиентские headers и внешний source этот carrier не получают. Fresh replay сохраняет прежнюю очистку volatile metadata и не восстанавливает удалённые ключи из старых headers. Lite normalization применяется как прежде и не позволяет metadata включить server-owned signal.
- Сохранить request-local различие explicit WS и auto WS. Только subscription auto WS может один раз перейти на HTTP на том же аккаунте и в той же reservation после доказанного pre-create handshake rejection:426, либо403 с `cf-mitigated: challenge`, либо Cloudflare HTML с известным challenge marker. Обычный403, auth/quota отказ, timeout, disconnect после отправки create, output или известный/неопределённый расход не разрешают fallback. REQUIRED capability не понижается до HTTP.
- Источник доказательства находится в handshake adapter; наружу передаётся typed boolean, не сырой response body/headers. Перед HTTP повторно применить transport-specific Lite normalization к original body; не повторять сам fallback, не делать дополнительные refresh/model calls. Все события и фактический usage HTTP попытки идут прежним settlement путём.

### 4. Управлять аккаунтами, группами и лимитами
admin change --authorize and validate--> persisted policy --apply to later admissions--> independently metered keys

Implementation Logic:
- Сохранить импорт/экспорт и OAuth refresh ChatGPT, типы external credentials, модельные ограничения, сроки подписки, остатки и reset timestamps с указанием свежести данных.
- Persisted usage сохраняет purchased-credit metadata и additional quota windows вместе с их timestamp; restart/import не заменяет известные остатки пустыми process-local данными. Самая новая явно заданная credit metadata может разрешить исчерпанное secondary window по legacy правилу, но не отменяет primary exhaustion. Monthly free-plan window остаётся governing long window. Для модели, связанной в действующем registry с additional quota, сохраняются canonical keys/aliases, plan restrictions и freshness: новые admissions используют собственные окна этой квоты, а не стандартные 5h/7d; отсутствующие или устаревшие необходимые данные дают явную data-unavailable ошибку. Registry/settings routing overrides не теряются. Этот фильтр не превращается в новый telemetry-denial для разрешённого established owner; authorisation/model/security ограничения по-прежнему действуют.
- Отсутствующее additional-quota поле сохраняет предыдущий snapshot, явное `[]` очищает его; старая выборка не перезаписывает новую. Import переносит последние явно заданные purchased credits, canonical additional windows, `blocked_at` и policy overrides. Новые admissions сохраняют 120-секундный cooldown и ограничения plan/tier/key/group.
- Группы аккаунтов остаются many-to-many. Ключ принадлежит одной группе; её одинаковые лимиты применяются каждому ключу с независимым потреблением. Изменение одной группы не меняет другую, даже при общем аккаунте.
- Лимит группы заменяет личный; при выходе сохраняется последняя эффективная конфигурация. Пустая группа не означает доступ ко всем аккаунтам. Изменение membership действует на следующие admissions, не прерывая уже допущенный ответ.
- Сохранить пароль/TOTP администратора, rate limiting входа, защиту изменения настроек, API-key scopes, шифрование секретов, firewall и корректное доверие reverse-proxy headers. Гостевого режима нет.
- Админка отправляет только явно изменённые settings и loaded `expectedVersion`; schema defaults и значения чужих контролов не превращаются в запись при каждом сохранении. Backend объединяет patch с актуальными настройками и сохраняет CAS-проверку. Это не позволяет неизвестным legacy полям блокировать изменение поддерживаемого переключателя или молча перезаписывать другой параметр.
- Windows OAuth help сохраняет authenticated `GET /api/settings/runtime/connect-address` и slash variant: trimmed `CODEX_LB_CONNECT_ADDRESS` выигрывает, иначе используется non-loopback IPv4 request host, первый пригодный IPv4 DNS имени либо само имя, для loopback/пустого host — `<codex-lb-ip-or-dns>`. DNS ограничен request context и коротким timeout; недоверенные forwarded host headers не меняют адрес. Возвращаемые значения пригодны для текстовой shell-инструкции, некорректная override конфигурация отвергается без её отражения в ошибке. Это информационный endpoint, не открытие callback listener и не изменение routing; provider calls отсутствуют.
- Proxy pools не реализуются. Общий исходящий прокси может быть настройкой установки; старую account-bound proxy policy при импорте нельзя молча превратить в direct egress.

### 4.2. Удалить аккаунт, не возвращая потраченный бюджет и старые права
authorized delete with history choice --mark the captured account incarnation deleted and revoke new access--> hidden credential-free tombstone --clean history in bounded existing maintenance batches--> cleaned tombstone --reimport with incremented incarnation--> fresh account

Observed Existing Logic:
- HTTP DELETE игнорирует `delete_history`; SQLite меняет только status/reason, оставляя credentials, memberships и видимый tombstone. Legacy отдельно фиксирует выбранный режим, отзывает доступ и ограниченными порциями удаляет или переатрибутирует историю. Go хранит raw usage, три folded источника и отдельные lifetime totals; восстановление totals только из raw потеряет уже свёрнутые данные.
- Financial settlement не завершает весь lifecycle: после него идут owner/outcome/archive callbacks, а file/control не всегда имеют reservation. Token refresh jobs keyed только account ID способны прочитать credentials нового импорта. Ожидание незавершённых reservations не устраняет эти гонки. Поэтому постоянный внутренний tombstone и монотонная incarnation проще общего счётчика всех операций или физического удаления с каскадами. Legacy остаётся read-only baseline.

Implementation Logic:
- Существующий admin DELETE принимает `delete_history` (по умолчанию false), валидирует boolean и сохраняет первый выбор для текущей incarnation. В одной транзакции закрывает новые admissions, удаляет credentials и memberships ключей/групп/источников, скрывает аккаунт из operational list/export/OAuth-existing check. Group/key/automation writers атомарно отвергают deleted tombstones: поздний save не возвращает удалённые назначения до reimport. Пустые scoped key/group/automation списки остаются закрытыми: удаление последнего member не включает all-accounts. Лимиты и их consumption не пересоздаются.
- Удаление external model source использует ту же границу отзыва для его backing account с сохранением истории; оно не оставляет зашифрованный API credential или старые key/source assignments. Отдельный новый режим history deletion для source API не добавляется.
- Incarnation начинается с0 для существующих/новых записей и увеличивается только при восстановлении deleted ID после завершения очистки истории. Reimport создаёт свежие credentials/metadata без старых grants, memberships, owners, warmup enablement или cached usage. Обязательный egress deny сохраняется. До завершения cleanup reimport возвращает явный conflict; неизвестный старый bill сам по себе не запрещает reimport.
- Маленькая durable deletion-policy запись хранит account ID/incarnation, выбранный режим и завершение cleanup. Первый bounded batch может выполняться в DELETE; последующие использует уже существующий maintenance, без нового worker. Quota/operational identity history очищается в обоих режимах. При false запросы и folded статистика получают deleted/orphan attribution, сохраняя общие и key totals; account total удаляется. При true raw/folded/error content удаляются, attributable report totals уменьшаются без возврата key-limit consumption. Implementation Logic:
- Один Go binary содержит сервер, адаптеры, встроенные assets админки и миграции. БД, ключ шифрования и рабочие данные внешние. SQLite обслуживается одним процессом; нет leader election, ring, межрепличных leases, PostgreSQL или объединения SQLite двух живых экземпляров.
- После проверки принадлежности/версии SQLite включается нативный WAL с `synchronous=FULL`: частые reserve/settlement commits не пересоздают rollback journal, но durability подтверждённых записей не ослабляется ради benchmark. Неизвестная/legacy база по-прежнему отклоняется до каких-либо schema/journal записей. Сравнение выполняется `scripts/compare-runtime.py` на временных базах и loopback Chat Completions stub; env-файлы установки и реальные provider credentials не загружаются.
- Поставка: бинарники для согласованных платформ, systemd unit для Linux, при необходимости один Dockerfile. Python/Rust/Bun/Node нужны только для legacy или сборки assets, не для запуска Go-сервера.
- Импорт читает согласованную копию данных и encryption key; оригинал не мигрируется in-place. По умолчанию сохраняются аккаунты, ключи, группы, настройки, ledger и статистика. Правило «только ошибки» не является разрешением удалить уже существующие данные.
- Если источник окажется PostgreSQL, нужен отдельный одноразовый путь импорта/экспорта; запрет PostgreSQL runtime не означает разрешение бросить данные источника. Секреты и private DB пока не исследованы.
- Аккаунты со снятой функцией обязательного proxy pool должны остаться недоступными до явного выбора безопасного маршрута; старые незавершённые reservations требуют reconciliation, а не безусловного сброса.
- Shutdown закрывает admission, ограниченно завершает активные turn/socket lifetimes и usage, затем освобождает ресурсы. Внешний proxy может удерживать клиентский порт при обновлении; открытые WebSocket не перемещаются между процессами автоматически.
- Cutover и rollback отдельно учитывают записи, появившиеся после переключения. Возврат старого бинарника к старой копии БД не считается безусловно безопасным откатом после новых списаний.
- Производительность сравнивается на одинаковом offline workload: RSS, CPU, goroutines, очередь, throughput, время до первого события и отмены. Не заявлять выигрыш по скорости ответа самой модели без измерений.
- Тот же `scripts/compare-runtime.py` получает JSON, paced SSE и cancel-after-first-content режимы; оба runtime проходят одинаковый loopback stub и temporary installations. Помимо CPU/RSS/latency выводятся TTFT, process threads/FD и задержка, за которую закрытие downstream прекращает upstream stream. Stub подтверждает фактический disconnect, а не только закрытие клиентского socket. Эти измерения не подменяют transport/accounting regression tests и не требуют production debug endpoint.

Tests:

- description: Бинарник запускается без env.local, отказ migration/key validation не открывает readiness; systemd restart не создаёт вторую БД или новый encryption key.

## Open questions

- Неблокирующее допущение: «ок» для пункта 7 означает SQLite без PostgreSQL в работающем сервере; это явно сообщено пользователю. Если источник данных PostgreSQL, импорт проектируется отдельно после получения доступа к согласованному snapshot.
- Z.AI/OpenAI-compatible source использует настроенный API key и объявленные capabilities. Специфические subscription credentials или quota polling произвольного стороннего провайдера не входят автоматически в совместимость Chat Completions/Responses; voice/image tools доступны только при подтверждённой поддержке выбранного источника.
- Проверка реального migration snapshot и production cutover требует отдельного согласования; текущая работа не включает чтение секретов, платные запросы или изменение live установки.
