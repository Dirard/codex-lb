# Один аккаунт в нескольких группах
- Last edited with skill pack: `0.2.2`

## Title and scope

Разрешить добавлять один аккаунт в несколько групп, независимо меняя состав каждой группы. Ключ по-прежнему принадлежит одной группе и получает только её лимиты.

## Planning anchor

`POST /api/account-groups/` и `PUT /api/account-groups/{group_id}` сейчас запрещают аккаунт из другой группы в `AccountGroupsService._validate_mutation`. `AccountGroupAccount` использует первичный ключ только по `account_id`. Изменение затрагивает валидацию и схему хранения.

Текущую `openspec/specs/account-groups/spec.md` необходимо amend. Контракты `api-keys` используются без изменения. Решений в `specs/` до этой задачи нет; `specs/spec-lifecycle/` содержит только правила процесса. Решение хранится в OpenSpec согласно проектному SSOT.

## Connected groups or observed existing logic

- Вход: `groups_api.py` проверяет dashboard session/write access и возвращает прежние envelope/status для ошибок. Формат `accountIds` менять не нужно.
- Хранение: `AccountGroupAccount` содержит две ссылки с CASCADE. Первичный ключ запрещает повтор аккаунта; индекс `group_id` обслуживает чтение состава. На таблицу членства не ссылаются другие таблицы.
- Изменение группы: `groups_repository.py#replace_assignments` уже удаляет только строки выбранного `group_id`. `groups_service.py` нормализует повторы ID, проверяет существование аккаунтов и синхронизирует лимиты только связанных ключей.
- Чтение/маршрутизация: `api_keys/service.py#_effective_assigned_account_ids` читает только `row.group.account_assignments`; после обновления группы выполняется инвалидация кэша ключей. Повтор аккаунта в разных группах не требует объединения политик.
- Интерфейс: `AccountGroupDialog` использует `AccountMultiSelect`, который не фильтрует аккаунты по принадлежности группе. Изменение компонентов не требуется.
- Проверки: существующие `test_account_groups_api.py`, `test_account_group_proxy.py`, `test_api_key_group_inheritance.py` и `test_account_group_migration.py` покрывают эти границы. Их дополняют случаи пересечения групп и безопасного отката.

## Use cases

### 1. Сохранить общие аккаунты независимо для каждой группы
список аккаунтов --проверить запрос--> допустимый состав --сохранить выбранную группу--> группы с независимым составом

Implementation Logic:

Удалить проверку `conflicting_assignments` и сам запрос. Сохранить нормализацию повторов, проверку существования аккаунтов, уникальность имени, блокировки и прежние транзакции. Замена состава остаётся ограниченной `group_id`; удаление группы удаляет только её связи. Лимиты и кэш ключей обновляются существующим механизмом.

Tests:
- description: Создание и редактирование двух групп с общим аккаунтом успешно; повтор ID внутри запроса сохраняется один раз; удаление связи или группы не изменяет вторую группу.
- description: Ключи двух групп используют общий аккаунт, но обновление лимитов и состава одной группы не меняет вторую; следующий запрос проверяет свежую область доступа, включая пустую группу.
- description: Неизвестные аккаунты, конфликт имени, неавторизованная запись и удаление группы с ключами сохраняют прежние ошибки.

### 2. Обновить схему без потери связей
существующие связи --заменить первичный ключ--> уникальные пары аккаунт-группа

Implementation Logic:

Новая ревизия после `20260907_000000_backfill_astra_request_costs` меняет первичный ключ на `(account_id, group_id)`. Использовать Alembic batch alteration с именем отражённого первичного ключа; для безымянного SQLite PK применить naming convention. Оставить `group_id` index и обе ссылки CASCADE. Не пересоздавать accounts, api_keys или их счётчики. Downgrade сначала проверяет аккаунты с несколькими связями и отказывает без изменений; при отсутствии пересечений возвращает ключ по account_id.

Tests:
- description: Upgrade сохраняет прежние связи и текущие лимиты/reservations; допускает вторую группу, запрещает дубликат пары, сохраняет FK/index и соответствует ORM metadata.
- description: Downgrade с пересечениями возвращает понятную ошибку и сохраняет строки; после явного удаления лишней связи downgrade/re-upgrade проходят без потери данных.

## Open questions

Блокирующих вопросов нет. Внешняя квота общего аккаунта остаётся физически общей: группы не дублируют квоту провайдера. Несколько групп на одном ключе, новые отчёты и обновление сервера вне задачи.
